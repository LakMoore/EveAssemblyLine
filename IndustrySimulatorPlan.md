## Plan: Ledger-Based Industry Simulator

Build a new deterministic simulator beside the current planner at `/api/plan/simulate`. Preserve the ten-list product shape through a versioned response adapter, but implement a clean internal model: type-only dependency discovery, complete demand declaration, one conserved asset-lot registry, append-only ledger transactions, ordered settlement, and presentation-ready projections. Leave `/api/plan` and the visible UI unchanged during this project.

### Assessment of the proposed approach

- Per-activity, per-location ledgers are the right organizing abstraction. They make locality, reservations, shortages, and phase ownership explicit.
- The proposed type-only fan-out is worthwhile. It should build and validate the reachable production/blueprint graph and seed zero-balance ledger accounts, but it must not copy quantities into multiple ledgers. Physical assets belong to one central lot registry and are only referenced by ledger transactions.
- Separate demand declaration from settlement. Manufacturing/reaction expansion must first declare all jobs and full input demand; invention and copying can then be derived from blueprint shortages. Only after every demand is known should stock be reserved. This avoids traversal-order bugs and makes reservations reproducible.
- Hauling should be planned after job counts and blueprint choices are fixed, but remote lots may be provisionally matched earlier to calculate the `after hauling` horizon. The hauling phase commits those matches into transfer tasks and never changes job counts.
- Reprocessing belongs late, as proposed. It may cover only residual demand and may consume only unreserved raw/compressed ores, compressed gas, and Metal Scraps/Reinforced Metal Scraps. Other ships/modules/assets are never candidates. Eligible reprocessable rows in stockpile inputs are reprocessing-source commitments whether or not `fromCompression` is set.
- Buying is the final sink for unresolved demand. It is locationless as an aggregate, but every row must retain destination and demand provenance so the UI can explain where purchases are needed.

### Core invariants

- All item, run, copy, attempt, slot, and reservation quantities are non-negative integers; percentages and time multipliers are the only fractional quantities.
- One source lot has one identity. Across all ledgers, total reservations against it never exceed its physical quantity.
- For every ledger account and supply horizon, `reserved <= available`; projected production, reprocessing, and purchases never count as physically available now.
- Demand is additive and immutable once declared. Settlement adds reservations/supply links; it does not rewrite the original demand.
- Recipe transforms conserve according to the exact SDE activity, products-per-run, complete-portion rules, ME, facility, and rounding rules recorded on the transaction.
- Every job, transfer, reprocessing selection, purchase, skill requirement, and warning has stable provenance back to stockpile demand and dependency edges.
- Results are deterministic under equivalent input ordering. Cycles, missing SDE records, contradictory policies, and unresolved locations produce typed warnings/errors rather than fallback recipes or guessed locations.
- Response assembly performs grouping, naming, and serialization only. It does not derive runs, availability, percentages, summaries, or schedules.

**Steps**

### Phase 1: Freeze contracts and characterize behavior

1. Extract the existing route-level Zod request validation into a shared schema module without changing `/api/plan` behavior. Add strict safe-integer validation for the simulator contract, reject a type present in both blacklists, validate owner pairs/location IDs, and preserve the existing compatibility input normalization.
2. Define `SimulatorRequestV1` as the current request plus a versioned `simulation` section. Add per-character IDs, free Manufacturing/Reactions/Science slots, per-activity time multipliers, relevant invention skill levels, optional decryptor choices, and scheduling policy. Existing facility profiles remain authoritative for manufacturing/reaction material bonuses; add location-specific copying/invention duration/consumption modifiers because the current aggregate fields cannot represent them.
3. Define policy defaults explicitly: expected invention output must cover 120% of required BPC runs; attempts are rounded up using supplied skills and selected decryptor, falling back to all relevant skills at level 3 and no decryptor. This is an expected-output safety factor, not a statistical confidence guarantee. Reject conflicting build/buy blacklists. Use current haul exclusions. Treat eligible stockpile reprocessing inputs as source commitments without consulting `fromCompression`.
4. Define `SimulationResultV1` and a separate compatibility adapter. Keep the same ten top-level lists, stable names, location buckets, and legacy fields, while adding authoritative fields described below. Add `simulatorVersion`, `policyVersion`, SDE revision, normalized-input hash, elapsed timings, and warning/error counts to metadata.
5. Create a characterization corpus from existing planner tests and sanitized fixture requests: T1, T2, T3, reactions, multi-stockpile/shared facilities, mixed ME BPO/BPC stock, active jobs, market orders, haul exclusions, reprocessing, blacklists, and unresolved assets. Capture current output only as a comparison oracle, not as the new correctness definition.

### Phase 2: Build the simulation foundation

6. Load one immutable `SimulationContext` per request from existing cached SDE indices: types, blueprint/product/activity indices, type materials, production groups, skills, volumes, facility profiles, and invention/decryptor data. Batch and cache all reachable lookups; never call ESI from the simulator.
7. Build a type-only dependency graph from every stockpile target. Model nodes by role and activity, not only type ID: product demand, manufacturing/reaction activity, production blueprint/formula, invention output BPC, source invention BPC, copying, and raw material. Record products-per-run and all alternative invention sources. Apply build/buy constraints while choosing edges; detect strongly connected components, cap node/edge counts, and stop affected branches with diagnostics.
8. Use the graph to create zero-balance accounts for every reachable `(activity, locationId, typeId)` combination. Retain stockpile IDs only on demand provenance and jobs; they never partition a physical ledger account. This primes the ledgers without moving stock and ensures later phases never create ad hoc semantic categories.
9. Normalize request assets once into an immutable source-lot registry. Preserve request index/synthetic lot ID, type, quantity/runs, owner, effective root location, blueprint instance ID and ME/TE, job/source status, availability time, and market/industry provenance. Classify physical-now, future-job-output, market commitment, blueprint, formula, and eligible-reprocessing lots. Unresolved lots stay diagnostic-only for location-constrained reservations.
10. Implement an append-only transaction journal and reducer. Required transaction kinds are demand declaration, source-lot reservation, blueprint-run reservation, production commitment, transfer commitment, reprocessing input/output commitment, purchase requirement, skill requirement, and warning. Post output first to its producing activity/location account, then explicitly commit any movement to the consuming account. Project it into de-duplicated Manufacturing, Reaction, Copying, Invention, Reprocessing, and Market ledgers keyed by activity and location; stockpiles remain demand provenance, not ledger identity.

### Phase 3: Declare complete production demand

11. Traverse quantified demand top-down over the discovered graph. For each unmet product demand, first net existing/future output according to its supply horizon, then choose buy/build per policy, compute exact required runs from product quantity per run, and declare a manufacturing or reaction job. Continue until all producible intermediates and raw inputs are declared. Memoize recipes, but retain separate demand provenance per stockpile and destination.
12. Resolve each manufacturing job into explicit blueprint allocations. Prefer usable local instances, then permitted remote instances; within a location choose the allocation with lowest material requirement, then shortest duration, then stable instance ID, while preserving finite BPC runs and reusable BPO capacity. Split jobs whenever ME/TE, blueprint kind, location, or applied facility modifiers differ. Do not average efficiencies across merged jobs.
13. For every manufacturing/reaction allocation, record required output, output per run, full runs, material demand per input using the existing material-rounding helper, selected blueprint/formula, applied ME/TE, facility and character time factors, and demand provenance. Formulas/BPOs are reusable but constrain concurrent installs; BPC runs are consumable and globally conserved.
14. Derive T2/T3 blueprint shortages from manufacturing allocations after current BPC runs, active invention output, and reusable originals are accounted for. For each invention path, calculate final probability from SDE base probability, supplied/fallback skills, and decryptor; calculate attempts so expected output runs meet the 120% target; record expected runs, safety margin, attempts, materials, source-BPC runs, ME/TE output, duration, and warnings about fallback policy.
15. Derive copying demand from source-BPC shortages created by invention and any production-copy requirements. Select source BPOs by location and availability, respect in-use originals and SDE maximum production limits, split copy jobs into explicit copies/licensed runs, and record copying materials, duration, source blueprint reservation, and resulting future BPC supply.
16. Accumulate skills and warnings during every graph/job phase. Deduplicate skills by skill ID at maximum required level while retaining the jobs that require them. Emit typed warnings for fallback skills/blueprints, missing facilities, missing SDE edges, blocked constraints, unavailable blueprints/formulas, cycles, unresolved assets, and incomplete scheduling context.

### Phase 4: Settle physical inventory and installability

17. After all activity demands exist, allocate physical local stock first through the central lot registry. Settle executable prerequisites in dependency order: copying, invention, leaf/upstream reaction and manufacturing jobs, then downstream/final manufacturing jobs. Within a level use stable stockpile/input order and reserve complete run kits, never fractions that cannot enable another whole run.
18. Perform a second allocation against permitted remote owned lots without creating tasks yet. Record provisional transfer reservations and calculate three separate job horizons: `readyNowRuns` from local physical stock, `readyAfterHaulingRuns` from local plus matched remote stock, and `readyAfterUpstreamRuns` from those plus committed copying/invention/reprocessing/production output. Also retain `requiredRuns` and `blockedRuns`; never collapse these meanings into one `runsAvailable` value.
19. Populate main/activity material rows with full demand, physical available now, remote matched, reserved now, reserved after hauling, available from production, available from invention/copying, available from reprocessing, unreserved physical surplus, and final unsatisfied demand. Assert `reservedNow <= availableNow` and the equivalent cumulative invariant at every horizon after each transaction.
20. Split manufacturing jobs server-side using per-character free slots and time multipliers. Assign complete install rows deterministically with longest-duration-first scheduling and stable character/slot tie-breaks; each row contains character ID, blueprint allocation, runs, exact inputs, duration, readiness horizon, and unscheduled remainder. Missing character capacity is a typed blocking warning, not an invented slot.
21. Produce one canonical reaction schedule using the same character-aware capacity model, but also return normalized per-run duration, formula count, run bounds, and horizon-specific installable runs so the client may quickly render alternative reaction schedules. The canonical response remains directly presentable; alternative interactive schedules are explicitly a client-side what-if view.

### Phase 5: Hauling, reprocessing, and buying

22. Convert provisional remote reservations into hauling transactions after all manufacturing, reaction, copying, and invention jobs are fixed. Match exact owner/location lots to exact destination demand, obey route/owner exclusions, prefer local then least-volume deterministic transfers, distinguish input-delivery from completion hauls, and never haul projected output or purchases. Preserve lot ownership in every task.
23. Run late reprocessing only against residual material demand. Candidate types are strictly raw ore, compressed ore, compressed gas, Metal Scraps, and Reinforced Metal Scraps. Exclude already reserved quantities and direct demand for the same source type. Use complete SDE portions, per-stockpile efficiency, aggregate yields before flooring, and deterministic scoring that prefers already-local inputs, then lower hauling volume and lower unusable surplus.
24. Represent local owned candidates as ready reprocessing rows; add transfer tasks for selected remote owned candidates; represent eligible stockpile-input commitments as future purchased reprocessing inputs. Credit outputs only in `availableFromReprocessing`, reserve/demand the exact source quantity in the main ledger, and retain unused coproduct as location surplus. Reprocessing may improve horizon coverage but cannot change declared jobs, blueprint choices, or full run counts.
25. Traverse every final ledger and create one locationless buying ledger from remaining unsatisfied demand. Aggregate display rows by type/category while retaining destination, stockpile, demanding job, source-vs-final-material intent, and buy-blacklist status. Keep ordinary materials and blueprint-original purchases mapped to the existing Buy tab groups. A buy-blacklisted unresolved demand remains blocked with a warning and is never silently purchased.

### Phase 6: Presentation adapter and endpoint

26. Build all ten output lists only from final ledger projections. Plan rows expose the full balance equation and demand provenance. Job rows expose required/ready/blocked runs, exact install rows, blueprint decisions, modifiers, inputs, output, and durations. Copy, invention, reprocessing, hauling, buying, skills, and warnings contain final display quantities and grouping keys; no UI arithmetic is required for the canonical view.
27. Map native fields to legacy `PlanResponse` fields in one documented adapter. For materials, legacy `availableQuantity` is physical owned supply allocated locally or through an allowed haul and excludes newly planned production, reprocessing, and purchases; `neededQuantity` is residual demand after physical supply plus committed non-purchase upstream output; `reprocessingQuantity` remains separately identifiable on job inputs. For jobs, legacy `runsAvailable` is `readyAfterHaulingRuns`, and input `completionPercent` is computed once from the complete-kit reservations behind that horizon. Preserve existing sort/group behavior and icons; never recalculate from already adapted rows. Add adapter contract tests for all ten tabs.
28. Add `/api/plan/simulate` with no-store behavior, shared validation, profiling, stable error shapes, and no auth/ESI side effects. Leave `/api/plan`, `calculatePlan`, storage, and the visible planner untouched. Document that future UI integration only needs a request-payload addition for character profiles and an endpoint switch; the existing visual structure and ten tabs remain valid, although richer fields can later replace current React calculations.

### Phase 7: Verification and controlled adoption

29. Unit-test graph discovery, SCC/cycle handling, journal reduction, lot and BPC-run conservation, exact material rounding, blueprint selection, expected invention coverage, copy derivation, complete-kit reservations, character slot assignment, haul matching/exclusions, reprocessing eligibility/yields, buying aggregation, and every response adapter mapping.
30. Add scenario tests for shared materials across jobs/stockpiles, shared activity locations, local-vs-remote competition, mixed-ME BPC depletion, BPO concurrency, active/future jobs, invention fallback and explicit decryptors, T3 paths, coproduct reprocessing, direct ore demand preservation, market commitments, zero slots, missing facilities, contradictory constraints, and unresolved locations.
31. Add property/invariant tests over randomized small graphs and lot sets: no negative balance, no over-reservation, no double use of BPC runs, transform conservation, stable results under input permutation, no purchase when another permitted supply satisfies demand, and every displayed aggregate equals its detailed rows.
32. Run the old and new calculators over the characterization corpus with a comparison harness. Classify differences as intentional contract corrections, bugs, or unexplained regressions; require zero unexplained differences before adoption. Do not write live user requests or asset ownership data to comparison logs.
33. Benchmark cold/warm SDE loads and representative large plans. Enforce the under-three-second target for typical warm requests, bounded graph size/depth, and profiler budgets per phase. Optimize indices or algorithms only from measured bottlenecks.
34. Run focused tests after each module, then `npm run lint`, `npm run format`, `npm run test`, `npm run typecheck`, and `npm run build`. Exercise `/api/plan/simulate` with representative requests and verify returned quantities independently against ledger totals. Update `CurrentPlan.md` and `README.md` with the simulator contract, phase order, policy defaults, limitations, and endpoint usage.

**Presentation-ready response additions**

- Plan material balances: `required`, `availableNow`, `availableAfterHauling`, `availableFromProduction`, `availableFromReprocessing`, `reservedNow`, `reservedAfterHauling`, `unreserved`, `unsatisfied`, `surplus`, and typed demand/supply provenance.
- Industry jobs: stable job/allocation IDs, stockpile IDs, product and blueprint IDs, exact blueprint instances and ME/TE, applied facility/skill modifiers, output per run, required/ready-after-each-horizon/blocked runs, exact inputs per allocation, duration, dependencies, and character/slot assignments.
- Invention/copying: source and output blueprint IDs, attempts/copies/licensed runs, final probability, expected output and 120% target, decryptor and skill source, materials, timing, existing/future BPC coverage, and explicit fallback warnings.
- Reprocessing: source lot/type/quantity/location/owner, portion count, efficiency, each material yield, local/after-haul/after-purchase state, allocated output, and coproduct surplus.
- Hauling and buying: exact source/destination/owner provenance for hauling; aggregate type totals plus per-destination breakdown for buying.
- Metadata: simulator/policy/SDE versions, input hash, timings, unresolved counts, and invariant diagnostics suitable for comparison without exposing tokens or secrets.

**Scope boundaries and decisions**

- Included: complete deterministic simulation, all ten output lists, location-aware activity ledgers, exact blueprint/run accounting, character-assigned manufacturing schedule, canonical but client-adjustable reaction schedule, invention/copying, late hauling/reprocessing, final buying, diagnostics, endpoint, and tests.
- Excluded: changing the current UI, switching `/api/plan`, ESI calls during planning, market price/cost optimization, route/path optimization, historical invention success modeling, generalized reprocessing of ships/modules, persistence migrations, and automatic production execution.
- The simulator launches through a separate endpoint. Old/new comparison is an offline/test acceptance tool, not production shadow traffic.
- The internal result is versioned and clean; a compatibility adapter preserves the established ten-list product surface.
- Current input/output shapes are not sufficient for the full requirement. Character assignment, science/invention policy, location-specific science bonuses, supply horizons, explicit reservations, and auditable blueprint decisions require additive versioned fields. This is a request-data integration change, but not a visual redesign.
